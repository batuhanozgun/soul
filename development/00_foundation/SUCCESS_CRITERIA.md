# SOUL SUCCESS CRITERIA

SOUL is successful only if the architecture can repeatedly create and operate task-specific agentic systems without depending on one long conversation, one agent's judgement, or hidden state.

A credible v1 must demonstrate all of the following across materially different pilot projects:

1. **Goal translation** — an intended outcome becomes an explicit, bounded work definition with known assumptions, unknowns, constraints, acceptance criteria, and human decision boundaries.
2. **Capability derivation** — the system identifies the capabilities, roles, tools, knowledge sources, controls, and verification needed by the task rather than relying on a permanently fixed team.
3. **State continuity** — a fresh session can continue from persistent project state without needing the previous conversation to be replayed.
4. **Context discipline** — agents receive the context required for their current responsibility without treating all available history as equally relevant or authoritative.
5. **Bounded agency** — roles and tools operate under explicit permissions and cannot silently enlarge their authority.
6. **Evidence-backed completion** — material completion claims can be traced to appropriate evidence and independent verification.
7. **Provenance where needed** — high-impact claims can be traced through their evidence and, when analytical work is involved, through computation, data, and source lineage appropriate to the decision risk.
8. **Independent verification** — the system does not rely on the producing agent, another agreeing model instance, or tool exit success as sole proof.
9. **Human governance** — the system asks the owner only for decisions that genuinely require human preference, judgement, authority, or approval; it does not offload researchable or technical decisions merely because they are difficult.
10. **Failure containment and recovery** — agent, tool, context, state, or verification failures become explicit system states with bounded recovery paths rather than silent drift or false completion.
11. **Controlled evolution** — repeated failures and validated lessons can become deterministic controls, tests, or architectural changes through an auditable change process.
12. **Capability extension** — when a required capability is absent, the system can safely specify, create or integrate, test, verify, and register that capability instead of assuming the user must design it.
13. **Observability** — a human can determine what is being done, why, by whom, with which evidence, under which decision, what is blocked, and why the system stopped.
14. **Domain transfer** — the same core architecture can support at least three substantially different pilots, including software production and analytical decision support, without encoding one pilot's domain workflow into the core.

No single pilot is sufficient evidence of generality.
